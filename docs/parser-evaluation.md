# phpMyAdmin SQL parser evaluation

Evaluated `phpmyadmin/sql-parser` **6.0.0** with PHP **8.5.10** and native
`mbstring`. The package was installed under ignored `.local/parser-evaluation/`;
no runtime dependencies, adapter behavior, or deployments changed.

## Assessment

The package is a useful lexer and statement/clause parser, but is **not a
complete expression AST or a ready-made MySQL-to-DSQL translator**. It merits
use as a building block, not immediate substitution for the existing translator.
Its lexer can separate quoted values, identifiers, comments, and punctuation.
Its statement objects expose operations such as pagination structurally. A DSQL
emitter and more complete expression handling would still be our responsibility.

One ordinary WordPress query fails parsing, while several invalid expressions
pass even in strict mode. Therefore parser success alone cannot authorize a
rewrite, and parser failure cannot yet be treated as evidence of invalid MySQL.

## Coverage

The existing synthetic WordPress smoke test passed all 24 checks on real DSQL
while its input SQL was captured locally. Evaluation itself never executes SQL.
Raw captured queries and detailed reports remain ignored; these are generic
aggregate results, not a deployment compatibility claim.

| Corpus | Queries | Parsed without errors | Built SQL reparsed without errors |
| --- | ---: | ---: | ---: |
| Inherited SQL fixtures | 504 | 504 | 504 |
| Distinct synthetic WordPress smoke queries | 148 | 147 | 147 |
| Handwritten probes, including intentionally invalid SQL | 31 | 27 | 27 |

The smoke capture contained 266 queries before exact-string deduplication. The
inherited corpus is predominantly SELECT: 410 SELECT, 48 SET, 15 SHOW, 14 INSERT,
10 UPDATE, and 7 DELETE statements. DDL coverage comes from the handwritten
probes, not those inherited fixtures.

The 31 probes comprise 24 expected-valid and seven expected-invalid statements.
The parser accepted 23 of the valid statements and rejected three invalid ones.
Valid probes included CTEs, window functions, subqueries, unions, upserts,
REPLACE, UPDATE with LIMIT, joined DELETE, JSON expressions, and CREATE/ALTER/
RENAME/DROP. This tests selected shapes, not complete feature coverage.

For every input, concatenating the lexer's raw tokens reproduced the original
SQL exactly. For successfully rebuilt statements, the sequence of raw string
literal tokens was unchanged, including Unicode, escaped quotes, backslashes,
actual NUL bytes, and SQL-looking text. These checks do **not** establish full
semantic equivalence or correctness on arbitrary inputs. The builder normalizes
formatting and can expand executable MySQL comments into SQL.

## Concrete limitations

### WordPress search ORDER BY

This valid MySQL shape reports parser errors:

```sql
SELECT id FROM wp_posts
ORDER BY title LIKE '%needle%' DESC, id DESC LIMIT 0, 1
```

The corresponding search query generated by WordPress also failed. Adding
parentheses around `title LIKE '%needle%'` makes the probe parse. This establishes
a small reproducer; it is not an implemented adapter workaround.

### Expression validation and structure

Both ordinary and strict parsing accepted these malformed expressions:

```sql
SELECT COALESCE(id, 0 FROM wp_posts
SELECT id FROM wp_posts WHERE id =
SELECT id + FROM wp_posts
```

They also accepted `COALESCE()` with no arguments. That fourth case requires
function-arity validation rather than just statement grammar validation.

A nested `COALESCE(NULLIF(LOWER(...)), CONCAT(...))` projection exposes its outer
function name, but keeps the expression in a string. Nested WHERE groups and
subqueries likewise remain partly string-based; parentheses can span multiple
condition components. There is no complete recursive tree of expression nodes
that we can simply visit to translate every operator or nested function.

### DSQL generation

The builder emits MySQL, including `LIMIT offset, count`. ANSI_QUOTES mode is
not a PostgreSQL/DSQL dialect backend. DSQL identities, asynchronous indexes,
upsert conflict targets, type/coercion differences, and schema-upgrade recovery
remain separate adapter responsibilities.

## Structural rewrite proof

`tests/parser-evaluation/rewrite.php` demonstrates six checks:

- parse one statement and identify its outer LIMIT;
- emit `LIMIT count OFFSET offset` from parsed fields;
- preserve a nested SELECT's LIMIT;
- preserve SQL-looking Unicode text in a quoted value byte for byte;
- convert backtick identifiers using token types;
- remove SQL_CALC_FOUND_ROWS from the statement's options.

The proof intentionally handles one known shape. It was not connected to
WordPress or promoted into the adapter. It does not implement MySQL string
escaping conversion, pagination counts, arbitrary unions, or expression semantics.

## Local performance

Five warmed passes over each corpus, without database or network time:

| Corpus | Full lex + parse median | Full lex + parse p95 | Lexer-only median |
| --- | ---: | ---: | ---: |
| Inherited fixtures | 0.183 ms | 0.574 ms | 0.112 ms |
| Distinct WordPress queries | 0.197 ms | 0.761 ms | 0.119 ms |
| Handwritten probes | 0.142 ms | 0.354 ms | 0.102 ms |

Peak PHP allocated memory for the combined evaluation was 4 MiB. This is whole
process allocation, not an isolated measure of parser memory. These are local
CLI measurements with native mbstring; they are not production latency estimates
or a comparison against the current adapter's end-to-end execution.

## Integration recommendation

1. Use the lexer as a candidate replacement for handwritten token/literal
   handling, retaining raw tokens and honoring MySQL modes. Token positions are
   Unicode character offsets, not byte offsets.
2. Translate explicitly supported statement components into a DSQL-specific
   representation. Close the search ORDER BY gap and add expression parsing
   before claiming general parser-based rewriting.
3. Keep the controlled DDL planner's existing validation and recovery boundaries;
   successful parsing must not bypass supported-schema checks.
4. Require differential result tests, including nested queries and write effects,
   before changing runtime SQL generation. Parse/build round trips alone are
   insufficient.

## Reproduce

From the repository root:

```sh
mkdir -p .local/parser-evaluation
composer require --working-dir=.local/parser-evaluation phpmyadmin/sql-parser:6.0.0
php tests/parser-evaluation/evaluate.php
php tests/parser-evaluation/rewrite.php
```

Without a smoke capture, the evaluator runs the inherited fixtures and handwritten
probes and reports zero WordPress queries. To include queries from the existing
synthetic local fixture, after following the README's fixture setup:

```sh
PGSSLROOTCERT=system php \
  -d auto_prepend_file=tests/parser-evaluation/capture.php \
  tests/dsql/smoke.php
php tests/parser-evaluation/evaluate.php
```

Use a trusted CA bundle instead of `system` with older libpq. The capture helper
only permits this test entrypoint and checks the local WordPress environment.
It writes raw SQL only to the ignored evaluation directory. Never use it to
capture production requests. Results are in `.local/parser-evaluation/report.json`.
